# Kashgar environment

The Bazaar stage is a point-symmetric, residential Kashgar-inspired paint arena. Twelve procedural houses connect streets, 2 m tea terraces, 4 m roofs and 6.4 m lookouts. Six roof links, stepped approaches, two courtyard gates, eight market stalls and a central fountain provide multiple routes. Fifty-two background houses, two timber gallery landmarks, poplars and mountains surround the playable area.

The user approved following the written direction because reference images were absent, then requested removing all GLBs in favor of the existing game’s architecture. Buildings now use shared Three.js primitives and Lambert materials. Kashgar requires no models, external environment textures, asset loaders, preparation tools or model-loading UI. The subsequently requested models belong to Turpan and Urumqi; see `TURPAN_ENVIRONMENT.md` and `URUMQI_ENVIRONMENT.md`.

## Files and ownership

```text
src/game/environment/
  environmentTypes.ts       # Placement and collision contracts
  kashgarLayout.ts          # Building styles, gameplay boxes and routes
  kashgarEnvironment.ts     # Instanced procedural buildings, props and skyline
  collision.ts              # Shared stair boxes and spatial broad phase
  cityNavigation.ts         # Layered surface graph and A* routes
  sceneResources.ts         # Shared scene resource cleanup
  staticBatches.ts          # Per-cell instancing shared with Turpan
```

`levels.ts` uses `KASHGAR_PRIMS`; the existing engine still owns movement, paint, actors, weapons, modes and scoring. Menu previews and the minimap derive geometry from the same layout. Detailed visual geometry never participates in movement, aim, projectile, camera or navigation queries.

The environment builds synchronously during `buildLevel()`. Stage changes dispose its geometry, materials, textures and instance buffers before constructing the next stage. The engine also cleans up shared scene resources on unmount. Kashgar needs no asset preparation step. The shared Vite build now excludes Urumqi authoring sources while retaining its optimized runtime models.

## Add a building or prop

1. Add a `BuildingPlacement` to the `north` list in `kashgarLayout.ts`. The south side is generated by point reflection. IDs should be stable and unique. Styles are `merchant`, `courtyard`, `terrace` and `lookout`; dimensions and palette provide variation.
2. Author stairs/decks connecting its roof. Do not add an unreachable gameplay roof. The rendered body fits the invisible collision envelope, stopping 0.16 m below the top so the separate paintable roof deck remains visible.
3. Add route landmarks and run `npm test`. Check roof entrances, stairs, underpasses and parapets from street height.
4. Repeated props belong in `StaticBatches`, using shared geometry and materials. Only gameplay cover needs a matching primitive in `KASHGAR_PRIMS`. Cloth, small pots, lights and foliage are decorative.
5. Keep residential details simple: plaster masses, cornices, arched timber doors, lattice windows, turquoise trim and timber ends. Use low-segment geometry and canvas patterns instead of imported meshes or texture maps.

```ts
{ id: "weavers", style: "merchant", x: 18, z: -15, w: 10, d: 10, h: 4 }
```

One game unit is one metre, Y is up, and the character is about 1.5 m tall. Building interiors are not navigable. Keep major new visual volumes aligned with collision; small facade trim can remain decorative.

## Collision and navigation

- `collisionOnly` boxes contribute to physics and previews; the procedural environment renders their corresponding buildings. `deco` skips collision; `paintable` lets a decorative roof deck use the turf material.
- `stairBoxes()` is shared by rendering, collision and tests. Treads have no gaps, a rise of at most 0.4 m here, and a `base` height for stairs between roofs. The engine’s step-up tolerance is 0.5 m.
- Keep routes at least 2.5–3 m wide. Roof links are 3.4 m wide. Corner parapets leave entrances clear and have simple box collision. Underpasses leave over 3 m headroom.
- `CollisionIndex` bins boxes into 6 m XZ cells for nearby movement and height queries. Projectile/camera casts intersect simple AABBs and the ground plane exactly, preserving open space under bridges.
- The city navigation graph samples walkable surfaces on a 1 m grid, keeping separate ground/roof nodes at the same XZ. Edges check intermediate foot/head clearance and step limits every 0.2 m. A* paths are cached per bot for roughly 1.1–1.4 seconds, with earlier replanning when the target moves substantially.
- Other arenas retain their water/obstacle navigation. Kashgar keeps existing bot roles and combat behavior; free-form combat strafing is suppressed while following city routes so it cannot steer bots off narrow links.
- Turf uses the original shared XZ grid. Ground and roof at the same XZ share ownership and scoring. Wall splats and swim climbing use the existing independent wall-ink records.

## Materials, lighting and performance

Architecture uses the game’s existing Lambert material approach with a shared palette. Ground, roofs, stairs and bridges retain the existing turf shader, with subtle procedural paving in Kashgar. Etles-inspired cloth, Uyghur street signs and soft contact cards are small canvas textures; signs redraw after the font loads.

Lighting is one warm directional sun plus cool sky/earth hemisphere illumination. There are no shadow-map passes, extra point lights or postprocessing chains. Repeated geometry is instanced in 32 m cells with bounds for frustum culling. Background houses have no collision.

Keep small props below a few hundred triangles, use shared geometry for door arches/window bars, and avoid separate materials per building. Kashgar requires no model transfers. The procedural-only app measured about 0.95 MiB after removing its GLBs; the current four-stage build, including Turpan and Urumqi models, is about 5.83 MiB with a shared engine chunk of about 724 kB. These totals exclude the remotely hosted interface font. See the Turpan and Urumqi guides for their separate model budgets.

The optional counter panel reports measured FPS, draw calls, triangles, geometry count and texture count. Local desktop measurements are useful comparisons, but they do not establish performance on physical lower-end phones. Character meshes remain a significant source of draw calls. The existing quality setting caps pixel ratio at 1.5 (high) or 1 (low).

## Verification

```sh
npm run dev
# Add ?perf=1 to the displayed local URL for renderer counters.
npm test
npm run build
npm run preview
```

The 19 core regression tests exercise existing match outcomes and actual movement/raycast functions against the authored city: spawn clearance, symmetry, all four tiers, every house roof, bridge underpasses and gate openings. The former Kashgar model-loader, asset-budget and loading-gate tests were removed with those features; Turpan adds nine separate regression tests for its requested model and vineyard routes. Browser checks verify the production city, immediate match admission, live painting and stage changes. Competitive route balance and target-device performance still need human playtesting.
